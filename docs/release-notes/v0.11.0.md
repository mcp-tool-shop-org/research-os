# v0.11.0 — Second Operator-Aloneness Repair Release

**Release date:** 2026-05-15
**npm:** `@mcptoolshop/research-os@0.11.0`
**Requires:** `ollama-intern-mcp@^2.4.0`

v0.11.0 closes the v0.2 operator-aloneness gate failure conditions surfaced 2026-05-15 (`operator_aloneness_dst_v0.2`, PASS_WITH_CONDITIONS but not authorization-grade). The release is a 4-slice repair arc covering 5 named findings: scope/boundary repair alignment (R-007), discover-time URL relevance check (R-008), paired source-content contamination defense at extraction and frame-critic layers (R-009 + R-011), and recover advisor fallback-cause visibility (R-010). v0.2 failed authorization because three independent contamination paths slipped past v0.10.0's defenses — `repair-scope --auto` filled `scope` but left `not` null so triage re-classified claims as `needs_scope_repair`, `llm-heuristic` discover presented real-but-unrelated PMC URLs as confidence-high candidates, and the extractor + frame-critic chain admitted 11 cancer-paper-derived claims with DST-framed text. The accept-floor invariant was the only designed defense that fired structurally; v0.11.0 closes the upstream gaps so v0.3 of the gate can fire against fresh operator runs.

## What shipped

### Slice 1 — scope/boundary repair alignment (R-007)

`claim repair-scope --auto` now fills BOTH `scope` AND `not` when both are null on a substantive claim at repair time. The boundary template mirrors the scope template's degradation shape (`not generalizing outside <publisher>'s <source_type> context` → `not generalizing outside <publisher>'s findings` → `not generalizing outside <source_type>` → `not generalizing outside the <section_purpose_short> scope`). The ledger gains optional `proposed_not` + `applied_not` fields (back-compat preserved; v0.10 records on disk parse cleanly). The interactive prompter shows the `Proposed not:` line alongside the scope proposal and prompts for `new not (blank to keep proposed)` only when boundary repair applies.

**Why this matters:** v0.2 of the operator-aloneness gate showed an external operator running `repair-scope --auto`, the ledger reporting 46 claims repaired, and then `claim triage` re-classifying 44 of those claims as `needs_scope_repair` because triage rule 1.2 requires BOTH fields on substantive claims. The CLI shipped, the ledger shipped, the gate stayed blocked. R-007 closes the v0.10 partial-close on R-001 — the repair surface now satisfies the triage condition that caused the repair.

**Explicit non-feature carried forward:** the reverse-asymmetric case (`scope=set, not=null`) stays outside repair-scope's candidate set. The R-001 close memo's "sneaky widening" caution applies — a future sibling action `repair_claim_boundary` (or unified `repair_claim_fit`) can address it if operator evidence demands.

### Slice 2 — discover hallucinated URL defense (R-008)

`discover run` now fetches each candidate URL's `<title>` tag (bounded: 64KB body, 5s timeout, 4-way concurrency) and computes keyword overlap against the discover query. Each candidate gains a `relevance` block:

```json
{
  "status": "verified" | "unverified" | "topic_mismatch",
  "fetched_title": "...",
  "query_keywords": ["..."],
  "matched_keywords": ["..."],
  "overlap_score": 0.43,
  "threshold": 0.2,
  "error": null,
  "checked_at": "..."
}
```

Default threshold `0.2` (at 7 query keywords, requires ≥2 to match). The v0.2 cancer/biochem/HIV URLs score 0; legitimate DST titles score 0.43–0.57. `approve --top N` structurally excludes `topic_mismatch`; `unverified` (network/fetch failure) is graceful — no over-blocking on transient errors. Operator override: `approve --candidate <id>` admits a flagged candidate; the relevance verdict stays on the ledger record for audit. Mirrors R-003's `clear_severities[]` "name the severity to clear" pattern without inventing a parallel override-ledger file.

`RESEARCH_OS_DISCOVER_RELEVANCE=0` env opt-out disables the check for offline/air-gapped workflows.

**Why this matters:** v0.2 evidence showed `llm-heuristic` discover returning 8 candidates for a DST workplace-research query, 3 of which were real PMC URLs (PMC7244163 Andalusia cancer mortality, PMC8130783 carboxylesterase biochem, PMC7354166 HIV lymphoma) pointing to entirely unrelated papers. The provider's titles and `why_relevant` strings were confabulations from the same LLM that picked the URLs — self-supporting and circular. Frame critic + accept-floor caught the contamination downstream by structural luck. R-008 closes the gap at the candidate admission layer, BEFORE operator approval and gather fetch.

### Slice 3 — source-content contamination defense (R-009 + R-011, paired)

**R-009 (extractor identity guard, HARD FAIL):** new source-card severity `source_identity_mismatch` fires when the LLM extractor's emitted `card.title` disagrees with the HTML `<title>` parsed from the fetched body. Reuses R-008's `tokenizeForRelevance` + `computeKeywordOverlap` helpers; same threshold semantics across layers (default 0.2). Operator override via `clear_severities[]` on the v0.4 source-card-overrides ledger. The v0.2 "rats and clonidine" / Barnes & Wagner 2009 confabulation case trips deterministically with overlap=0.

**R-011 (frame-critic source-content precheck):** new frame-exclusion reason `source_content_mismatch`. The frame critic now computes a source-content signature once per source (bounded 64KB, dedupe, length≥3, stopword filter) and compares the signature to each claim's `asserts` text via R-008's overlap helper. Below threshold → `frame_excluded: true` with reason `source_content_mismatch`; the LLM critic call is short-circuited. The v0.2 11-cancer-paper-DST-claim case has overlap ≤10% with the source body vocabulary (only place names like "Almeria"/"Spain" appear in both) and trips the precheck before the LLM critic ever fires. Legitimate DST claims score 50–80% on real DST source content.

`RESEARCH_OS_FRAME_SOURCE_CONTENT=0` env opt-out disables the precheck if the LLM critic alone is preferred. `CriticTally.source_content_mismatch` counter (optional for back-compat) surfaces how many drafts were caught by the deterministic precheck vs the LLM critic.

**Defense-layer independence verified:** when R-009 is disabled (no `<title>` tag in body), R-011 still catches the v0.2 cancer-paper-DST-claim case via vocabulary mismatch. When R-011 is disabled (`sourceRawText` not threaded through), R-009 still catches the v0.2 Barnes & Wagner identity case at the audit + extract quarantine layer. Together with R-008's admission defense, the three layers form the source-content contamination guard pipeline.

### Slice 4 — recover MD fallback-cause visibility (R-010)

The recover advisor's deterministic-fallback path now surfaces the cause + optional timing in the operator-facing markdown. New closed enum `FALLBACK_CAUSES` (3 values: `tier_timeout | mcp_error | retry_exhausted`) classifies why the fallback fired. `tier_timeout` matches MCP errors containing the literal `TIER_TIMEOUT` marker; `retry_exhausted` for verifier-rejected-twice; `mcp_error` for other MCP-layer failures. Optional structured timing `prose_error.timing_ms = { elapsed_ms, budget_ms }` is populated when the rejection string carries the `elapsed=NNNNms budget=NNNNms` shape `ollama-intern-mcp` emits on `TIER_TIMEOUT`. Absence is honest — never fabricated.

The recover markdown now renders, under each fallback section:

```
### Why the AI advisor fell back

**Cause:** AI advisor timed out (TIER_TIMEOUT) — elapsed 15012ms over 15000ms budget.

The recovery guidance below was generated deterministically from pack law
rather than the AI advisor. The fallback recovery action and pack-law
forbiddings are unchanged.

Raw error and timing are preserved at `prose_error.last_rejection_reason`
(and `prose_error.timing_ms` when parseable) in
`recovery/blocked-section-recovery.json` for full inspection.
```

The top callout gains a per-cause suffix (e.g., `Deterministic fallback applied to: 2 section(s) (AI advisor exhausted) — 2 timeout`). The AI-advisor-success path renders no fallback messaging (regression-guarded by test 4 in `r010-recover-fallback-visibility.test.ts`).

**Why this matters:** v0.2 showed both sections hitting `TIER_TIMEOUT` (elapsed=15012ms / 15009ms over 15000ms budget); the recovery engine correctly fell back to deterministic rendering and produced usable output, but the cause was buried inside `last_rejection_reason` JSON — invisible to operators reading the markdown. R-010 surfaces the cause + timing prominently while preserving the existing fallback selection unchanged. This is operator-clarity, not operator-blocker. The advisor timeout budget (15000ms or whatever `ollama-intern-mcp` has configured), model routing, and recovery recommendations are all unchanged.

## Doctrine notes

- **The accept-floor invariant is the floor of safety, not a designed defense layer.** v0.2 showed the unwaiveable `accepted_claim_floor` was the only structural defense that fired on the 11 cancer-paper-DST-claim case; R-008, R-009, R-011 close that gap with three independent upstream defenses so the accept-floor stops doing double duty.
- **Additive evolution preserves frozen-pack receipts.** All v0.11 slices ship optional schema fields and new enum members on existing closed enums; no field-rename, no schema-flip, no receipt regression. Eleventh consecutive byte-identical 4-pack run is the receipt.
- **Operator-aloneness gates surface load-bearing product gaps the engineering view cannot see.** v0.2 found five findings that would have been silent product defects without the gate. R-007 specifically would have been invisible without an external operator following the `recover` advisor's instructed repair and discovering the triage-vs-repair-surface disagreement.

## Surprising / non-obvious during release

- **The v0.2 TIER_TIMEOUT case made it through the v0.10 release** because the recovery engine's fallback path was sound — the deterministic recommendation came out usable, just without the AI's contrastive framing. The bug was operator-clarity, not correctness. R-010's fix is surface-only.
- **Defense-layer precedence is structural, not policy.** R-009 quarantines the SOURCE upstream of the extractor; R-011 evaluates DRAFT CLAIMS inside the critic loop; R-008 evaluates URL CANDIDATES inside the discover loop. So if R-009 fires, R-011 has no drafts to evaluate; if R-008 quarantines a URL, R-009 has nothing to extract from. This is correct precedence — defending earlier is better than later.
- **No new advisor actions.** `RECOVERY_ACTIONS` stays at 8 values; the v0.11 arc closes upstream gaps so the existing advisor surface keeps doing what it already did, just with more reliable upstream evidence.
