# अनुसंधान-ओएस (रिसर्च-ओएस)

`research-os` एक जेनरेट किए गए दस्तावेज़ को एक स्थिर प्रमाणिक संग्रह में बदल देता है। यह मूल जानकारी को संरक्षित करता है, दावों को संश्लेषण से अलग करता है, गेट के माध्यम से तत्परता सुनिश्चित करता है, समीक्षक और छूट निर्णयों को रिकॉर्ड करता है, और एक पैकेज प्रकाशित करता है जिसके दावों को ट्रैक और सत्यापित किया जा सकता है।

यह आपसे मॉडल पर विश्वास करने के लिए नहीं कहता है। यह आपको यह तय करने के लिए आवश्यक उपकरण प्रदान करता है कि क्या मॉडल, स्रोत और संश्लेषण पर विश्वास किया जा सकता है।

## यह क्या है।

`research-os` एक नियंत्रण प्रणाली है जो "मैं X पर शोध करना चाहता हूं" और एक स्थिर, प्रमाण-आधारित डेटाबेस के बीच संबंध स्थापित करती है। यह खोज के शुरुआती चरणों को प्रमाणों को प्राप्त करने से, कच्चे डेटा निष्कर्षण को छांटे गए दावों से, विरोधाभासों का पता लगाने को विरोधाभासों के समाधान से, और समीक्षा निर्णयों को संश्लेषण निर्णयों से अलग करती है। प्रत्येक चरण में, जानकारी केवल जोड़ने के लिए लिखी जाती है; प्रत्येक निष्कर्ष केवल उन दर्ज की गई जानकारियों के आधार पर निकाला जाता है, न कि किसी धारणा के आधार पर।

यह कोई रिपोर्ट जनरेटर नहीं है। यह कोई एलएलएम (LLM) प्रबंधन प्रणाली भी नहीं है। यह आपके लिए संश्लेषण (सिंथेसिस) नहीं लिखता है। यह उन शर्तों को लागू करता है जिनके तहत संश्लेषण शुरू किया जा सकता है।

फ्रीज किए गए पैकेज [`mcp-tool-shop-org/research-packs`](https://github.com/mcp-tool-shop-org/research-packs) में संग्रहीत हैं – ये लाइव हैं, और इसमें छह बंद "डॉगफूड" प्रयोगों को कवर करने वाले चार पैकेज शामिल हैं। v1.0 के लिए रोडमैप [`docs/roadmap.md`](docs/roadmap.md) में देखें।

v0.1 को दो परीक्षणों में जांचा गया। पहले परीक्षण में, "रिसर्च-ओएस" ने अपनी ही विशिष्टताओं की जांच की, जिसमें v0.1.0 जारी होने से पहले सात त्रुटियां पाई गईं, जिनमें से प्रत्येक को ठीक करने की आवश्यकता थी और जिसके लिए एक नियम या एकीकरण पैटर्न की आवश्यकता थी। दूसरे परीक्षण (v1 प्रयोग 1: कॉमफीयूआई वर्कफ़्लो की स्थिरता, 11 सत्र, एक ऐसा डोमेन जिसमें "रिसर्च-ओएस" के साथ कोई शब्दावली समानता नहीं है) को 2026-05-09 को बंद कर दिया गया: पैकेज फ्रीज किया गया, संग्रह लाइव है, पैटर्न 2 को `22b5dba` कमिट के माध्यम से लागू किया गया। v0.1 के परीक्षण के परिणाम [`docs/dogfood-proof.md`](docs/dogfood-proof.md) में उपलब्ध हैं; प्रयोग 1 के परीक्षण के परिणाम [`docs/experiment-1-proof.md`](docs/experiment-1-proof.md) में उपलब्ध हैं। लाइव हैंडबुक: <https://mcp-tool-shop-org.github.io/research-os/handbook/>।

## स्थापना

**आवश्यकताएँ:** Node.js ≥ 20।

```bash
npm install -g @mcptoolshop/research-os
```

उन योगदानकर्ताओं के लिए जो स्रोत कोड से निर्माण कर रहे हैं:

```bash
git clone https://github.com/mcp-tool-shop-org/research-os.git
cd research-os
npm install
npm run build
npm link
```

## शुरुआत

```bash
# Create a new research-pack
research-os init "How should X be structured?"

# Add a section
research-os section add 01-landscape --purpose "Map the current landscape"

# Discover and approve sources, then gather
research-os discover run 01-landscape
research-os discover approve 01-landscape --top 8
research-os gather 01-landscape --approved

# Run the per-section chain
research-os claim extract 01-landscape
research-os claim audit-density 01-landscape
research-os claim triage 01-landscape
research-os contradict map 01-landscape --triaged-only
research-os review 01-landscape --triaged-only --preset hermes-two-pass --profile hermes-two-pass
research-os review-promote 01-landscape --profile hermes-two-pass
research-os gate 01-landscape
research-os section report 01-landscape

# Pack-level finish
research-os audit
research-os index build --all
research-os cowork handoff
research-os synth workspace   # only if handoff returned synthesis_ready
research-os freeze

# Export to the research-packs archive
research-os pack publish \
  --to <research-packs>/packages/<name>
```

> **`freeze` आउटपुट पर ध्यान दें।** `research-os freeze` कमांड चुपचाप चलता है, यह प्रत्येक "कैनोनिकल" फ़ाइल की जांच करता है और सामग्री हैश की गणना करता है – इस कमांड के लिए कोई भी प्रगति संकेतक नहीं है। बड़े पैकेजों के लिए, यह कुछ सेकंड तक चल सकता है और फिर कुछ भी प्रिंट कर सकता है। जब यह समाप्त होता है, तो यह एक ही परिणाम ब्लॉक प्रिंट करता है (`PASS` / `REFUSED` और पाथ)। इस अंतराल को सिस्टम के हैंग होने के रूप में न समझें।

> **`--force` चेतावनी।** `--force` विकल्प लक्षित पैकेज निर्देशिका को साफ़ करता है और उसे बदल देता है। उत्पन्न पैकेज आउटपुट के अंदर मैन्युअल रूप से बनाए गए फ़ाइलों को न रखें। इसके बजाय, मूल फ़ाइलों (दावे, स्रोत, संश्लेषण) या संबंधित फ़ाइलों को संपादित करें। पूर्ण स्वीकृति अनुबंध + अस्वीकृति के मामले: [`docs/pack-publish.md`](docs/pack-publish.md)।

**एक वास्तविक उदाहरण के लिए**, `research-os-packs/research-os-spec/` पर मौजूद 'डॉगफूड' पैकेज देखें - प्रत्येक फ़ाइल, प्रत्येक रिकॉर्ड, प्रत्येक स्थिति, प्रत्येक 'फ्रीज' फ़िंगरप्रिंट, सभी केवल अपेंड करने योग्य लॉग फ़ाइलों में मौजूद हैं। इसी पैकेज ने `docs/dogfood-proof.md` बनाया है।

**स्थानीय रूप से [`ollama-intern-mcp@^2.4.0`](https://github.com/mcp-tool-shop-org/ollama-intern-mcp) की आवश्यकता है** LLM निष्कर्षण, वर्गीकरण, समीक्षा और खोज के लिए। MCP सर्वर `OLLAMA_INTERN_MCP_BIN` पर्यावरण चर या PATH के माध्यम से खोजा जाता है। डिफ़ॉल्ट मॉडल `hermes3:8b` है; `OLLAMA_INTERN_MODEL=<model>` (या प्रति-कॉल `--model <name>`) के साथ इसे बदलें। यदि Ollama डिफ़ॉल्ट `localhost:11434` पर नहीं है, तो `OLLAMA_HOST` सेट करें।

**नियम 3:** एलएलएम (LLM) कभी भी किसी प्रमाणिक पाठ का निर्माण नहीं करता है। "रिसर्च-ओएस" (research-os) एक निश्चित प्रकार की अंशों की सूची (लेजर) बनाता है, जिसमें स्थिर पहचान संख्याएँ होती हैं, जैसे कि `ex_<स्रोत_आईडी_हेक्स>_001`। एलएलएम इन अंशों की पहचान संख्याओं का चयन करता है, और "रिसर्च-ओएस" वास्तविक पाठ की प्रतिलिपि बनाता है। "पुन: वाक्यांश बनाकर उद्धरण" करने में विफलता की स्थिति संरचनात्मक रूप से असंभव है।

**नियम 14:** निष्कर्षण और समीक्षा के बीच, `रिसर्च-ओएस (Research-OS) दावा वर्गीकरण` (claim triage) डुप्लिकेट प्रविष्टियों को हटाता है, प्रत्येक स्रोत से योगदान की सीमा निर्धारित करता है, और कम महत्व वाले उम्मीदवारों को अस्थायी रूप से रखता है। यह वर्गीकरण प्रक्रिया `claims.jsonl` फ़ाइल में कोई बदलाव नहीं करती है; अस्थायी रूप से रखे गए दावों को मूल रिकॉर्ड में ही रखा जाता है।

## v0.1 संस्करण का कार्यप्रवाह श्रृंखला।

```
discover
→ gather
→ claim extract
→ claim audit-density
→ claim triage
→ contradict map
→ contradict resolve
→ review
→ review-promote
→ gate
→ section report
→ audit
→ index build
→ cowork handoff
→ synth workspace
→ freeze
```

प्रत्येक चरण एक कमांड-लाइन इंटरफेस (CLI) कमांड है। प्रत्येक चरण केवल अपेंड (जोड़ना) करने वाले फ़ाइलों में लिखता है। कोई भी चरण संश्लेषण नहीं करता है, समाधान नहीं करता है, या नई जानकारी नहीं बनाता है - ये अपरिवर्तनीय नियम लागू किए जाते हैं, उन पर भरोसा नहीं किया जाता। समीक्षा प्रक्रिया में, दावे स्वीकार या अस्वीकार किए जाते हैं या सुधार का अनुरोध किया जाता है; गेट प्रक्रिया इन समीक्षा निर्णयों का उपयोग `synthesis_eligible` की गणना करने के लिए करती है; 'फ्रीज' अंतिम सुरक्षा लॉक है जो किसी भी पैकेज को 'पूर्ण' के रूप में चिह्नित करने से इनकार करता है, जब तक कि सभी स्तर सहमत न हों। `v0.1` के प्रमाण के लिए, जो दर्शाता है कि यह श्रृंखला अंत-से-अंत तक काम करती है, [docs/dogfood-proof.md](docs/dogfood-proof.md) देखें।

यह *खोज → सारांश → सुंदर रिपोर्ट* का एक संरचनात्मक विकल्प है। यह श्रृंखला ही उत्पाद है।

|------|---------|
| `research-os` | नियंत्रण प्रणाली / कमांड-लाइन इंटरफेस / गेट / समन्वय नियम (यह रिपॉजिटरी) |
| `research-pack` | एक शोध प्रयास के लिए उत्पन्न रिपॉजिटरी फ़ाइल |

| `research receipt` | यह दर्शाता है कि एक अनुभाग ने स्रोत/दावा/गेट जांच पास कर ली है |

## सुरक्षा

`research-os` एक स्थानीय-प्रथम कमांड-लाइन इंटरफेस है। यह उन शोध-पैकेज निर्देशिकाओं में फ़ाइलों को पढ़ता और लिखता है जिन्हें आप निर्दिष्ट करते हैं, और (जब `gather` का उपयोग किया जाता है) स्रोत यूआरएल प्राप्त करने के लिए बाहरी HTTP अनुरोध भेजता है जिन्हें आप प्रदान करते हैं। यह निम्नलिखित नहीं करता है: कोई सर्वर नहीं चलाता, इनकमिंग कनेक्शन स्वीकार नहीं करता, क्रेडेंशियल संग्रहीत नहीं करता, या टेलीमेट्री नहीं भेजता। किसी भी गुप्त जानकारी को पैकेज फ़ाइलों में नहीं लिखा जाता है। भेद्यता रिपोर्टिंग नीति के लिए [SECURITY.md](SECURITY.md) देखें।

## समीक्षक अंशांकन

v0.5.0 समीक्षक अंशांकन को अधिक टिकाऊ बनाता है। एक समीक्षक प्रोफाइल पर इसलिए भरोसा नहीं किया जाता क्योंकि
यह केवल एक बार चलाया गया था; यह संरचित, पूर्वनिर्धारित विफलता परिणामों और
कई बार चलाने के बाद प्राप्त आंकड़ों के आधार पर एक स्थिति प्राप्त करता है। v0.6.0 उत्पादन
समीक्षा प्रक्रिया और अंशांकन प्रणाली में निश्चित (डिटरमिनिस्टिक) समीक्षक विकल्पों को जोड़ता है।

**वर्तमान में कोई भी प्रोफाइल `trusted_baseline` के रूप में स्वीकार नहीं किया गया है।** रिपॉजिटरी में मौजूद
मानक परिणाम दर्शाते हैं कि `hermes-two-pass=failed`, `mistral-nemo-two-pass=conditional_pass`,
`hermes-single-pass=comparison_only`, `hermes-two-pass-deterministic=failed`। यह
जानबूझकर किया गया है: विश्वास बार-बार प्राप्त होने वाले, पूर्वनिर्धारित विफलता प्रमाणों के माध्यम से अर्जित किया जाता है, न कि केवल अनुमान के आधार पर।
`hermes-two-pass-deterministic` परिणाम में एक संरचनात्मक मॉडल-क्षमता अंतर है
(6 निर्णय प्रकारों में से 2 उत्पन्न किए गए; 3/6 की आवश्यकता है) जो विचलन (वैरिएंस) की समस्या नहीं है।

अंशांकन परिणाम `calibration/reviewer-profiles/<profile>/seeded-v1.{json,md}` में उपलब्ध हैं।
प्रत्येक परिणाम सात मानदंडों के विरुद्ध PASS/FAIL रिकॉर्ड करता है, चार स्थिति लेबल
(`trusted_baseline`, `conditional_pass`, `failed`, `comparison_only`), और
ईमानदारी से बताता है कि परीक्षण प्रणाली क्या नहीं कर सकती (`needs_contradiction_mapping`
`seeded-v1` से दुर्गम है)। [CHANGELOG.md](CHANGELOG.md) देखें।

```bash
# Single-run calibration (quick local check)
node scripts/reviewer-calibration.mjs --model hermes3:8b --two-pass --profile hermes-two-pass

# Multi-run aggregate calibration (canonical evidence — 3 runs, median-based PASS/FAIL)
node scripts/reviewer-calibration.mjs --model hermes3:8b --two-pass --profile hermes-two-pass --runs 3

# Deterministic multi-run calibration (temperature + seed explicit in receipt)
node scripts/reviewer-calibration.mjs --model hermes3:8b --two-pass \
  --temperature 0 --seed 7 --runs 3 --profile hermes-two-pass-deterministic

# Promote a section's review — auto-populates calibration_summary from pack-relative receipt
research-os review-promote 01-section --pack <pack> --profile hermes-two-pass
```

जब `--runs <n>` का उपयोग किया जाता है, तो प्रत्येक रन के लिए परिणाम `<profile>/runs/run-NNN.json` में लिखे जाते हैं
और एक समग्र परिणाम (माध्य-आधारित मानदंडों और बार-बार होने वाली विफलता का पता लगाने के साथ)
`<profile>/seeded-v1.{json,md}` में लिखा जाता है। समग्र परिणाम में `receipt_kind: 'aggregate'` होता है
जो इसे एकल-रन परिणामों से अलग करता है। एकल-रन मोड (`--runs 1` या छोड़ा गया) मौजूदा
सीधे लिखने के व्यवहार को बनाए रखता है।

**निश्चित (डिटरमिनिस्टिक) समीक्षक प्रोफाइल** — `research.yaml` में `review_profiles.<name>.reviewer_options` का उपयोग करें
`temperature`, `seed`, और अन्य Ollama सैंपलिंग पैरामीटर को उत्पादन समीक्षा प्रक्रिया में
प्रत्येक `OllamaInternReviewer` निर्माण में शामिल करने के लिए। `hermes-two-pass-deterministic` प्रोफाइल
एक अंतर्निहित उदाहरण के रूप में उपलब्ध है। [`docs/experiment-6-proof.md`](docs/experiment-6-proof.md) और
[समीक्षक अंशांकन पुस्तिका पृष्ठ](https://mcp-tool-shop-org.github.io/research-os/handbook/reviewer-calibration/) देखें।

## नया संस्करण v0.10.0 — ऑपरेटर-अकेलापन सुधार रिलीज

v0.10.0, 2026-05-15 को सामने आए v0.1 ऑपरेटर-अकेलापन गेट विफलता स्थितियों को ठीक करता है (`operator_aloneness_dst_v0.1`, FAIL)। चार सुधारों को एक साथ लागू किया गया है: रिकवरी रूटिंग संरेखण, स्कोप-मरम्मत के लिए CLI, पेयर किए गए सोर्स-कार्ड ऑडिट को मजबूत करना, और सटीक स्थिति जानकारी। v0.1 गेट विफल हो गया क्योंकि एक बाहरी ऑपरेटर ने तीन स्वतंत्र बाधाओं का सामना किया — `recover` ने गलत अनब्लॉक पथ की सिफारिश की, `scope=null` दावों को ठीक करने के लिए कोई CLI मौजूद नहीं था, और सोर्स-कार्ड ऑडिट में एक नकली COVID-19 कार्ड का पता चला, जो 1035-बाइट APA Incapsula बॉट-चेक खंड से निकाला गया था। v0.10.0 इन बाधाओं को दूर करता है।

### आप क्या चला सकते हैं

```sh
research-os claim repair-scope <section-id> [--auto | --interactive]
                                              # fix claims that arrived with scope=null
research-os recover pack                       # advisor now reads gate.blocking_reasons[] first
research-os source-card audit                  # severities now include bot-check + word-count quarantine
```

### सुधार का तरीका

```
gate blocked  →  recover diagnose (now gate-routed)  →  recover advise (repair_claim_scope action)
              ↓
              claim repair-scope (new CLI; auto or interactive)
              ↓
              re-run review + gate; claims promote without hand-editing claims.jsonl
```

दावा निष्कर्षण से पहले, सोर्स-कार्ड ऑडिट अब बॉट-चेक/CAPTCHA खंडों (`bot_check_or_captcha_detected`, HARD FAIL) और नकली, कम डेटा वाले/उच्च निष्कर्षण वाले स्रोतों (`extraction_suspect_word_count_mismatch`, WARN AND QUARANTINE) को अलग करता है। ऑपरेटर मौजूदा v0.4 सोर्स-कार्ड ओवरराइड रजिस्टर पर नए `clear_severities[]` फ़ील्ड के माध्यम से इन सेटिंग्स को बदल सकते हैं।

अब, प्रत्येक डेटा प्राप्त करने पर, `gather_outcome` नामक एक 5-मान वाला एनम (`ok | fetch_failed | extraction_skipped | extraction_failed | bot_check_detected`) प्रदर्शित होता है। v0.1 में मौजूद भ्रमित वाक्यांश `"Failed (ok HTTP 200)"` अब मौजूद नहीं है; PDF अब `extraction_skipped` के रूप में प्रदर्शित होते हैं, `Failed` के रूप में नहीं।

### नियमों की सीमा

यह सुधार एक अतिरिक्त सुधार है। पहले के नियमों का पालन किया गया है: `accepted_claim_floor` अपरिवर्तनीय है; रिकवरी सलाहकार अभी भी अपरिवर्तनीय विफलताओं के लिए `apply_waiver` की सिफारिश नहीं करता है। बंद `FailureShape` एनम में कोई बदलाव नहीं किया गया है; R-002 केवल मौजूदा नौ आकृतियों में गेट-स्टेट रूटिंग जोड़ता है। `RECOVERY_ACTIONS` में 7 से 8 बंद मानों तक वृद्धि हुई है (`repair_claim_scope` जोड़ा गया)। गंभीरता क्वारंटीन कभी भी स्पष्ट ऑपरेटर ओवरराइड के बिना ऑडिट गेट से आगे स्वचालित रूप से नहीं बढ़ता है (नया `clear_severities[]` फ़ील्ड एक दर्ज ऑपरेटर निर्णय है, जो केवल जोड़ने की अनुमति है)।

सभी चार स्थिर पैकों के लिए, स्थिर-पैकेज प्रतिगमन, v0.3.3 बेसलाइन के समान है - लगातार छठा रिलीज जिसमें यह सच है।

### research-os क्या नहीं है (और v0.10.0 क्या होने का दावा नहीं करता है)

- यह ऑपरेटर-अकेलेपन की जांच नहीं करता, और यह जांच नए पैकों पर नहीं की गई है। v0.10.0, v0.1 गेट की विफलता की स्थितियों को ठीक करता है; v0.2, ऑपरेटर-अकेलेपन गेट के खिलाफ इस npm रिलीज़ के एक अलग सत्र में काम करता है और इसमें आगे सुधार हो सकते हैं। v0.10.0, v0.2 के लिए आवश्यक है, यह प्रमाण नहीं है।
- यह बाहरी उपयोगकर्ताओं द्वारा व्यापक रूप से परीक्षण नहीं किया गया है, केवल आंतरिक परीक्षणों तक ही सीमित है। छह आंतरिक परीक्षण किए गए हैं - जिनमें से एक आत्म-संदर्भित है, और पांच अन्य क्षेत्रों (ComfyUI, XRPL, Godot, समीक्षक-कैलिब्रेशन, नियतात्मक-समीक्षक) से संबंधित हैं - लेकिन बाहरी ऑपरेटरों द्वारा बड़े पैमाने पर उपयोग अभी भी भविष्य का कार्य है।
- यह एक पूर्ण-पैकेज संश्लेषण लेखक नहीं है। v0.10.0, v0.9 के अनुभाग-स्कोप (`synth section`) और आंशिक-पैकेज-स्कोप (`synth pack --partial`) सुविधाओं को बरकरार रखता है, जिनमें से प्रत्येक में स्पष्ट रूप से पैकेज की तैयारी की जानकारी दी गई है। पूर्ण-पैकेज संश्लेषण के लिए अभी भी एक `synthesis_ready` पैकेज और `synth workspace` के माध्यम से स्वीकृत दावा आईडी के खिलाफ मानव (या Cowork) द्वारा बनाया जाना आवश्यक है।
- यह किसी भी समीक्षक मॉडल का समर्थन नहीं करता है। v0.10.0 डिफ़ॉल्ट रूप से `trusted_baseline` समीक्षक प्रोफ़ाइल के साथ नहीं आता है; कैलिब्रेशन रसीदें समर्थन नहीं हैं, बल्कि प्रमाण हैं। मौजूदा v0.6.0 कैलिब्रेशन रसीदें v0.8.0 MCP आर्किटेक्चर से पहले की हैं और MCP पथ के तहत उन्हें फिर से कैलिब्रेट नहीं किया गया है। [समीक्षक कैलिब्रेशन हैंडबुक पृष्ठ](https://mcp-tool-shop-org.github.io/research-os/handbook/reviewer-calibration/) देखें।
- इसमें पुराने संस्करणों के अवशेष नहीं हैं। v0.4 से पहले के स्थिर पैकों में `research_os_version: '0.1.0'` है, क्योंकि v0.4 से पहले एक हार्डकोडेड स्कैफोल्ड स्थिरांक का उपयोग किया गया था; यह सुधार v0.4.0 में लागू किया गया था, लेकिन पुराने स्थिर पैकों को कानून 15 के तहत बदला नहीं जा सकता (देखें [`handbook/known-limitations`](https://mcp-tool-shop-org.github.io/research-os/handbook/known-limitations/)।
- यह npm पर प्रमाणित नहीं है। Sigstore प्रमाणीकरण को भविष्य के रिलीज़ में लागू किया जाएगा; पैकेज-shasum और GitHub रिलीज़ कमिट के माध्यम से v0.10.0 npm पैकेजों को सत्यापित करें।
- यह क्लाउड-आधारित समाधान का विकल्प नहीं है। v0.7.x से `local-first-vs-cloud-research/` पर उत्पाद प्रदर्शन से पता चला कि क्लाउड में पठनीयता और ऑपरेटर के बोझ के मामले में फायदे हैं; v0.10.0 यह दावा नहीं करता है कि इन फायदों को समाप्त कर दिया गया है।

### ज्ञात सीमाएँ

v0.10.0, पिछले रिलीज़ से प्राप्त तीन ज्ञात सीमाओं के साथ आता है, जो ऑपरेटरों को दिखाई देती हैं। प्रत्येक सीमा को [हैंडबुक ज्ञात-सीमाएं पृष्ठ](https://mcp-tool-shop-org.github.io/research-os/handbook/known-limitations/) और [CHANGELOG.md](CHANGELOG.md) में प्रलेखित किया गया है। इनमें से कोई भी रिलीज़ को अवरुद्ध नहीं करता है; सभी के लिए एक परिभाषित रिकवरी या शमन पथ है।

- **B-E-001 — v0.4 से पहले के स्थिर-पैकेज संस्करण स्टैंप एक ऐतिहासिक अवशेष है।** v0.3.3 से v0.6.0 तक प्रकाशित स्थिर पैकों में `research_os_version: "0.1.0"` `pack.manifest.json` और `pack/research.yaml` में है, क्योंकि v0.4 से पहले एक हार्डकोडेड स्कैफोल्ड स्थिरांक का उपयोग किया गया था। यह सुधार v0.4.0 में लागू किया गया था (अब स्कैफोल्ड लाइव `RESEARCH_OS_VERSION` आयात करता है); पुराने स्थिर पैकों को कानून 15 के तहत बदला नहीं जा सकता। प्रभावित पैकों के अंदर मौजूद JSON फ़ाइलों में उनके वर्तमान संस्करण मौजूद हैं।
- **B-E-004 — npm प्रमाणीकरण को भविष्य के रिलीज़ में लागू किया जाएगा।** v0.10.0 npm tarball केवल पैकेज-shasum के माध्यम से सत्यापित होता है। प्रकाशन प्रक्रिया को एक CI वर्कफ़्लो में स्थानांतरित करने से sigstore OIDC के साथ टकराव होता है (TranslateGemma 12B स्थानीय रूप से चलता है); यह माइग्रेशन भविष्य के रिलीज़ में योजनाबद्ध है। पैकेज-shasum और GitHub रिलीज़ कमिट के माध्यम से v0.10.0 npm पैकेजों को सत्यापित करें।
- **B-A-003 — इंडेक्सर स्कीमा-संस्करण माइग्रेशन प्रलेखित है, लेकिन लागू नहीं है।** v0.10.0 में एक राइट-साइड `SCHEMA_VERSION` पूर्णांक शामिल है, लेकिन कोई रीड-साइड माइग्रेशन रनर नहीं है। प्रलेखित `SCHEMA_VERSION` में वृद्धि होने पर, `.research-os/index.sqlite` को हटाएं और `research-os index build --all` को फिर से चलाएं। स्वयं पैकेज अप्रभावित रहता है - इंडेक्सर साक्ष्य + दावों पर एक त्वरण परत है (कानून 8); पुनर्निर्माण idempotent है।

**v0.10.0 में, किसी भी `trusted_baseline` समीक्षक प्रोफाइल को अनुमति नहीं है।** यह एक जानबूझकर किया गया सुरक्षा उपाय है, कोई कमी नहीं: रिपॉजिटरी में मौजूद "कैलिब्रेशन रसीदें" (`hermes-two-pass=failed`, `mistral-nemo-two-pass=conditional_pass`, `hermes-single-pass=comparison_only`, `hermes-two-pass-deterministic=failed`) इस बात का प्रमाण दर्ज करती हैं। विश्वास अर्जित किया जाता है, अनुमानित नहीं किया जाता, और यह बार-बार किए गए "सीडेड-विफलता" परीक्षणों के माध्यम से प्राप्त होता है। ये रसीदें v0.8.0 के एमसीपी आर्किटेक्चर से पहले की हैं और एमसीपी पथ के तहत इन्हें फिर से "बेसलाइन" नहीं किया गया है।
