# अनुसंधान-ओएस (रिसर्च-ओएस)

`research-os` एक जेनरेट किए गए दस्तावेज़ को एक स्थिर प्रमाणिक संग्रह में बदल देता है। यह मूल जानकारी को संरक्षित करता है, दावों को संश्लेषण से अलग करता है, गेट के माध्यम से तत्परता सुनिश्चित करता है, समीक्षक और छूट निर्णयों को रिकॉर्ड करता है, और एक पैकेज प्रकाशित करता है जिसके दावों को ट्रैक और सत्यापित किया जा सकता है।

यह आपसे मॉडल पर विश्वास करने के लिए नहीं कहता है। यह आपको यह तय करने के लिए आवश्यक उपकरण प्रदान करता है कि क्या मॉडल, स्रोत और संश्लेषण पर विश्वास किया जा सकता है।

## यह क्या है।

`research-os` एक नियंत्रण प्रणाली है जो "मैं X पर शोध करना चाहता हूं" और एक स्थिर, प्रमाण-आधारित डेटाबेस के बीच संबंध स्थापित करती है। यह खोज के शुरुआती चरणों को प्रमाणों को प्राप्त करने से, कच्चे डेटा निष्कर्षण को छांटे गए दावों से, विरोधाभासों का पता लगाने को विरोधाभासों के समाधान से, और समीक्षा निर्णयों को संश्लेषण निर्णयों से अलग करती है। प्रत्येक चरण में, जानकारी केवल जोड़ने के लिए लिखी जाती है; प्रत्येक निष्कर्ष केवल उन दर्ज की गई जानकारियों के आधार पर निकाला जाता है, न कि किसी धारणा के आधार पर।

यह कोई रिपोर्ट जनरेटर नहीं है। यह कोई एलएलएम (LLM) प्रबंधन प्रणाली भी नहीं है। यह आपके लिए संश्लेषण (सिंथेसिस) नहीं लिखता है। यह उन शर्तों को लागू करता है जिनके तहत संश्लेषण शुरू किया जा सकता है।

फ्रीज किए गए पैकेज [`mcp-tool-shop-org/research-packs`](https://github.com/mcp-tool-shop-org/research-packs) में संग्रहीत हैं – ये लाइव हैं, और इसमें छह बंद "डॉगफूड" प्रयोगों को कवर करने वाले चार पैकेज शामिल हैं। v1.0 के लिए रोडमैप [`docs/roadmap.md`](docs/roadmap.md) में देखें।

v0.1 को दो परीक्षणों में जांचा गया। पहले परीक्षण में, "रिसर्च-ओएस" ने अपनी ही विशिष्टताओं की जांच की, जिसमें v0.1.0 जारी होने से पहले सात त्रुटियां पाई गईं, जिनमें से प्रत्येक को ठीक करने की आवश्यकता थी और जिसके लिए एक नियम या एकीकरण पैटर्न की आवश्यकता थी। दूसरे परीक्षण (v1 प्रयोग 1: कॉमफीयूआई वर्कफ़्लो की स्थिरता, 11 सत्र, एक ऐसा डोमेन जिसमें "रिसर्च-ओएस" के साथ कोई शब्दावली समानता नहीं है) को 2026-05-09 को बंद कर दिया गया: पैकेज फ्रीज किया गया, संग्रह लाइव है, पैटर्न 2 को `22b5dba` कमिट के माध्यम से लागू किया गया। v0.1 के परीक्षण के परिणाम [`docs/dogfood-proof.md`](docs/dogfood-proof.md) में उपलब्ध हैं; प्रयोग 1 के परीक्षण के परिणाम [`docs/experiment-1-proof.md`](docs/experiment-1-proof.md) में उपलब्ध हैं। लाइव हैंडबुक: <https://mcp-tool-shop-org.github.io/research-os/handbook/>।

## स्थापना

**आवश्यकताएँ:** Node.js ≥ 20।

```bash
npm install -g @mcptoolshop/research-os
```

उन योगदानकर्ताओं के लिए जो स्रोत कोड से निर्माण कर रहे हैं:

```bash
git clone https://github.com/mcp-tool-shop-org/research-os.git
cd research-os
npm install
npm run build
npm link
```

## शुरुआत

```bash
# Create a new research-pack
research-os init "How should X be structured?"

# Add a section
research-os section add 01-landscape --purpose "Map the current landscape"

# Discover and approve sources, then gather
research-os discover run 01-landscape
research-os discover approve 01-landscape --top 8
research-os gather 01-landscape --approved

# Run the per-section chain
research-os claim extract 01-landscape
research-os claim audit-density 01-landscape
research-os claim triage 01-landscape
research-os contradict map 01-landscape --triaged-only
research-os review 01-landscape --triaged-only --preset hermes-two-pass --profile hermes-two-pass
research-os review-promote 01-landscape --profile hermes-two-pass
research-os gate 01-landscape
research-os section report 01-landscape

# Pack-level finish
research-os audit
research-os index build --all
research-os cowork handoff
research-os synth workspace   # only if handoff returned synthesis_ready
research-os freeze

# Export to the research-packs archive
research-os pack publish \
  --to <research-packs>/packages/<name>
```

> **`freeze` आउटपुट पर ध्यान दें।** `research-os freeze` कमांड चुपचाप चलता है, यह प्रत्येक "कैनोनिकल" फ़ाइल की जांच करता है और सामग्री हैश की गणना करता है – इस कमांड के लिए कोई भी प्रगति संकेतक नहीं है। बड़े पैकेजों के लिए, यह कुछ सेकंड तक चल सकता है और फिर कुछ भी प्रिंट कर सकता है। जब यह समाप्त होता है, तो यह एक ही परिणाम ब्लॉक प्रिंट करता है (`PASS` / `REFUSED` और पाथ)। इस अंतराल को सिस्टम के हैंग होने के रूप में न समझें।

> **`--force` चेतावनी।** `--force` विकल्प लक्षित पैकेज निर्देशिका को साफ़ करता है और उसे बदल देता है। उत्पन्न पैकेज आउटपुट के अंदर मैन्युअल रूप से बनाए गए फ़ाइलों को न रखें। इसके बजाय, मूल फ़ाइलों (दावे, स्रोत, संश्लेषण) या संबंधित फ़ाइलों को संपादित करें। पूर्ण स्वीकृति अनुबंध + अस्वीकृति के मामले: [`docs/pack-publish.md`](docs/pack-publish.md)।

**एक वास्तविक उदाहरण के लिए**, `research-os-packs/research-os-spec/` पर मौजूद 'डॉगफूड' पैकेज देखें - प्रत्येक फ़ाइल, प्रत्येक रिकॉर्ड, प्रत्येक स्थिति, प्रत्येक 'फ्रीज' फ़िंगरप्रिंट, सभी केवल अपेंड करने योग्य लॉग फ़ाइलों में मौजूद हैं। इसी पैकेज ने `docs/dogfood-proof.md` बनाया है।

**स्थानीय रूप से [`ollama-intern-mcp@^2.4.0`](https://github.com/mcp-tool-shop-org/ollama-intern-mcp) की आवश्यकता है** LLM निष्कर्षण, वर्गीकरण, समीक्षा और खोज के लिए। MCP सर्वर `OLLAMA_INTERN_MCP_BIN` पर्यावरण चर या PATH के माध्यम से खोजा जाता है। डिफ़ॉल्ट मॉडल `hermes3:8b` है; `OLLAMA_INTERN_MODEL=<model>` (या प्रति-कॉल `--model <name>`) के साथ इसे बदलें। यदि Ollama डिफ़ॉल्ट `localhost:11434` पर नहीं है, तो `OLLAMA_HOST` सेट करें।

**नियम 3:** एलएलएम (LLM) कभी भी किसी प्रमाणिक पाठ का निर्माण नहीं करता है। "रिसर्च-ओएस" (research-os) एक निश्चित प्रकार की अंशों की सूची (लेजर) बनाता है, जिसमें स्थिर पहचान संख्याएँ होती हैं, जैसे कि `ex_<स्रोत_आईडी_हेक्स>_001`। एलएलएम इन अंशों की पहचान संख्याओं का चयन करता है, और "रिसर्च-ओएस" वास्तविक पाठ की प्रतिलिपि बनाता है। "पुन: वाक्यांश बनाकर उद्धरण" करने में विफलता की स्थिति संरचनात्मक रूप से असंभव है।

**नियम 14:** निष्कर्षण और समीक्षा के बीच, `रिसर्च-ओएस (Research-OS) दावा वर्गीकरण` (claim triage) डुप्लिकेट प्रविष्टियों को हटाता है, प्रत्येक स्रोत से योगदान की सीमा निर्धारित करता है, और कम महत्व वाले उम्मीदवारों को अस्थायी रूप से रखता है। यह वर्गीकरण प्रक्रिया `claims.jsonl` फ़ाइल में कोई बदलाव नहीं करती है; अस्थायी रूप से रखे गए दावों को मूल रिकॉर्ड में ही रखा जाता है।

## v0.1 संस्करण का कार्यप्रवाह श्रृंखला।

```
discover
→ gather
→ claim extract
→ claim audit-density
→ claim triage
→ contradict map
→ contradict resolve
→ review
→ review-promote
→ gate
→ section report
→ audit
→ index build
→ cowork handoff
→ synth workspace
→ freeze
```

प्रत्येक चरण एक कमांड-लाइन इंटरफेस (CLI) कमांड है। प्रत्येक चरण केवल अपेंड (जोड़ना) करने वाले फ़ाइलों में लिखता है। कोई भी चरण संश्लेषण नहीं करता है, समाधान नहीं करता है, या नई जानकारी नहीं बनाता है - ये अपरिवर्तनीय नियम लागू किए जाते हैं, उन पर भरोसा नहीं किया जाता। समीक्षा प्रक्रिया में, दावे स्वीकार या अस्वीकार किए जाते हैं या सुधार का अनुरोध किया जाता है; गेट प्रक्रिया इन समीक्षा निर्णयों का उपयोग `synthesis_eligible` की गणना करने के लिए करती है; 'फ्रीज' अंतिम सुरक्षा लॉक है जो किसी भी पैकेज को 'पूर्ण' के रूप में चिह्नित करने से इनकार करता है, जब तक कि सभी स्तर सहमत न हों। `v0.1` के प्रमाण के लिए, जो दर्शाता है कि यह श्रृंखला अंत-से-अंत तक काम करती है, [docs/dogfood-proof.md](docs/dogfood-proof.md) देखें।

यह *खोज → सारांश → सुंदर रिपोर्ट* का एक संरचनात्मक विकल्प है। यह श्रृंखला ही उत्पाद है।

|------|---------|

## सुरक्षा

`research-os` एक स्थानीय-प्रथम कमांड-लाइन इंटरफेस है। यह उन शोध-पैकेज निर्देशिकाओं में फ़ाइलों को पढ़ता और लिखता है जिन्हें आप निर्दिष्ट करते हैं, और (जब `gather` का उपयोग किया जाता है) स्रोत यूआरएल प्राप्त करने के लिए बाहरी HTTP अनुरोध भेजता है जिन्हें आप प्रदान करते हैं। यह निम्नलिखित नहीं करता है: कोई सर्वर नहीं चलाता, इनकमिंग कनेक्शन स्वीकार नहीं करता, क्रेडेंशियल संग्रहीत नहीं करता, या टेलीमेट्री नहीं भेजता। किसी भी गुप्त जानकारी को पैकेज फ़ाइलों में नहीं लिखा जाता है। भेद्यता रिपोर्टिंग नीति के लिए [SECURITY.md](SECURITY.md) देखें।

## समीक्षक अंशांकन

v0.5.0 समीक्षक अंशांकन को अधिक टिकाऊ बनाता है। एक समीक्षक प्रोफाइल पर इसलिए भरोसा नहीं किया जाता क्योंकि
यह केवल एक बार चलाया गया था; यह संरचित, पूर्वनिर्धारित विफलता परिणामों और
कई बार चलाने के बाद प्राप्त आंकड़ों के आधार पर एक स्थिति प्राप्त करता है। v0.6.0 उत्पादन
समीक्षा प्रक्रिया और अंशांकन प्रणाली में निश्चित (डिटरमिनिस्टिक) समीक्षक विकल्पों को जोड़ता है।

**वर्तमान में कोई भी प्रोफाइल `trusted_baseline` के रूप में स्वीकार नहीं किया गया है।** रिपॉजिटरी में मौजूद
मानक परिणाम दर्शाते हैं कि `hermes-two-pass=failed`, `mistral-nemo-two-pass=conditional_pass`,
`hermes-single-pass=comparison_only`, `hermes-two-pass-deterministic=failed`। यह
जानबूझकर किया गया है: विश्वास बार-बार प्राप्त होने वाले, पूर्वनिर्धारित विफलता प्रमाणों के माध्यम से अर्जित किया जाता है, न कि केवल अनुमान के आधार पर।
`hermes-two-pass-deterministic` परिणाम में एक संरचनात्मक मॉडल-क्षमता अंतर है
(6 निर्णय प्रकारों में से 2 उत्पन्न किए गए; 3/6 की आवश्यकता है) जो विचलन (वैरिएंस) की समस्या नहीं है।

अंशांकन परिणाम `calibration/reviewer-profiles/<profile>/seeded-v1.{json,md}` में उपलब्ध हैं।
प्रत्येक परिणाम सात मानदंडों के विरुद्ध PASS/FAIL रिकॉर्ड करता है, चार स्थिति लेबल
(`trusted_baseline`, `conditional_pass`, `failed`, `comparison_only`), और
ईमानदारी से बताता है कि परीक्षण प्रणाली क्या नहीं कर सकती (`needs_contradiction_mapping`
`seeded-v1` से दुर्गम है)। [CHANGELOG.md](CHANGELOG.md) देखें।

```bash
# Single-run calibration (quick local check)
node scripts/reviewer-calibration.mjs --model hermes3:8b --two-pass --profile hermes-two-pass

# Multi-run aggregate calibration (canonical evidence — 3 runs, median-based PASS/FAIL)
node scripts/reviewer-calibration.mjs --model hermes3:8b --two-pass --profile hermes-two-pass --runs 3

# Deterministic multi-run calibration (temperature + seed explicit in receipt)
node scripts/reviewer-calibration.mjs --model hermes3:8b --two-pass \
  --temperature 0 --seed 7 --runs 3 --profile hermes-two-pass-deterministic

# Promote a section's review — auto-populates calibration_summary from pack-relative receipt
research-os review-promote 01-section --pack <pack> --profile hermes-two-pass
```

जब `--runs <n>` का उपयोग किया जाता है, तो प्रत्येक रन के लिए परिणाम `<profile>/runs/run-NNN.json` में लिखे जाते हैं
और एक समग्र परिणाम (माध्य-आधारित मानदंडों और बार-बार होने वाली विफलता का पता लगाने के साथ)
`<profile>/seeded-v1.{json,md}` में लिखा जाता है। समग्र परिणाम में `receipt_kind: 'aggregate'` होता है
जो इसे एकल-रन परिणामों से अलग करता है। एकल-रन मोड (`--runs 1` या छोड़ा गया) मौजूदा
सीधे लिखने के व्यवहार को बनाए रखता है।

**निश्चित (डिटरमिनिस्टिक) समीक्षक प्रोफाइल** — `research.yaml` में `review_profiles.<name>.reviewer_options` का उपयोग करें
`temperature`, `seed`, और अन्य Ollama सैंपलिंग पैरामीटर को उत्पादन समीक्षा प्रक्रिया में
प्रत्येक `OllamaInternReviewer` निर्माण में शामिल करने के लिए। `hermes-two-pass-deterministic` प्रोफाइल
एक अंतर्निहित उदाहरण के रूप में उपलब्ध है। [`docs/experiment-6-proof.md`](docs/experiment-6-proof.md) और
[समीक्षक अंशांकन पुस्तिका पृष्ठ](https://mcp-tool-shop-org.github.io/research-os/handbook/reviewer-calibration/) देखें।

### नया क्या है

**R-019 — आंतरिक MCP स्तर-बजट क्लाइंट कनेक्शन।** R-018 का `--planner-timeout-ms <N>` ध्वज (और `RESEARCH_OS_SYNTH_PLANNER_TIMEOUT_MS` पर्यावरण चर) अब प्लानर/ड्राफ्टर/सत्यापनकर्ता से `ollama_extract.tier_budget_ms_override` तक जाता है, और `runWithTimeoutAndFallback` तक पहुंचता है जो `ollama-intern-mcp/src/guardrails/timeouts.ts:61` पर स्थित है। आंतरिक, प्रति-स्तर समय-सीमा तंत्र, जिसने v0.4 के पुन: परीक्षण के दौरान `elapsed=15018ms budget=15000ms` त्रुटि उत्पन्न की थी, अब सीधे ऑपरेटर के बजट का सम्मान करता है। R-018 रैपर को अनसुलझे-वादे के कारण होने वाले रुकावटों के खिलाफ एक बाहरी सुरक्षा उपाय के रूप में बनाए रखा गया है (अन्य विफलताओं को पकड़ने वाले रैपर वास्तव में काम कर सकते हैं)। इसके लिए `ollama-intern-mcp@>=2.6.0` की आवश्यकता है; पुराने संस्करण नए स्कीमा फ़ील्ड को चुपचाप अनदेखा कर देंगे (R-018 रैपर अभी भी अपने मूल स्तर पर काम करता है - यह एक अनुकूलनीय समाधान है)।

**R-020 (केवल D) — `no_answer_cluster` रिकवरी सतह।** जब प्लानर किसी भी स्वीकृत दावे को "उत्तर" भूमिका देने से इनकार करता है, तो त्रुटि अब `section-synthesis.json` में इनलाइन `recovery_actions[]` (`narrow_section_purpose` + `add_on_topic_sources`) प्रदर्शित करती है, `section-synthesis.md` में एक रेंडर किया गया `## Recovery actions` मार्कडाउन ब्लॉक (जिसमें `action_id` शीर्षक, स्पष्टीकरण पाठ और एक `fenced command_hint` कोड ब्लॉक शामिल है), और एक एकल-पंक्ति `stderr` संकेत (`[synth] no_answer_cluster — कार्रवाई योग्य चरणों के लिए `section-synthesis.md` में "Recovery actions" ब्लॉक देखें`)। कार्रवाई सूची एक एकल स्रोत है जिसे कार्रवाई-ग्राफ रिकवरी पथ के साथ साझा किया जाता है; स्टैंडअलोन-कमांड और इनलाइन-विफलता-बॉडी पथों के बीच कोई विचलन नहीं है। **R-020 के प्लानर प्रॉम्प्ट ट्यून (A-half) का प्रयास किया गया था और उसे वापस ले लिया गया** — iter-1 ने चुपचाप गलत संश्लेषण उत्पन्न किया (LLM ने प्रतिकूल फिक्स्चर पर सकारात्मक-प्रभाव वाले दावों से शून्य-प्रभाव वाले उत्तर बनाए; सत्यापनकर्ता ने उल्टे निषेध को `faithful` के रूप में स्वीकार किया); iter-2 का HARD GUARDRAIL भ्रम को दूर करने में विफल रहा। ऑपरेटर के एक-पुनरावृत्ति नियम के अनुसार, प्रॉम्प्ट और 3 v3-पिन किए गए परीक्षण फ़ाइलें वापस ले ली गईं; `PROSE_PROMPT_VERSION` `section-prose-v3` पर बना हुआ है। एक महत्वपूर्ण सीख: संरचनात्मक लाइव पुन:प्रदर्शन सफल हो सकता है जबकि संश्लेषित सामग्री चुपचाप गलत हो सकती है; प्रतिकूल फिक्स्चर पर मैनुअल पाठ निरीक्षण निषेध/दायरा/वाक्यांश के उलटने का पता लगाने के लिए आवश्यक है।

**R-021 — कॉन्ट्राडिक्ट-मैप ऑटो-मोड में हैंग-टाइमआउट + हेयुरिस्टिक फॉल-थ्रू + दृश्य प्रगति।** नया `--auto-mode-pair-timeout-ms <N>` (डिफ़ॉल्ट 90000; पहले R-021 से पहले के हार्डकोडेड 120 सेकंड से कम, v0.4 फिक्सचर पर गेट-माप किए गए वार्म hermes3:8b के अनुसार: न्यूनतम 6.2 सेकंड, माध्य 8.4 सेकंड, अधिकतम 8.8 सेकंड → 90 सेकंड का डिफ़ॉल्ट, जिसमें ≥81 सेकंड का अतिरिक्त स्थान है)। नया `--auto-mode-fall-through-after-n-timeouts <N>` (डिफ़ॉल्ट 5; स्वचालित हेयुरिस्टिक फॉल-थ्रू के लिए लगातार विफलता सीमा; सफल `type:none` वर्गीकरण काउंटर को रीसेट करते हैं)। संबंधित एनवायरनमेंट वेरिएबल। नया stdout स्टार्ट लाइन (`auto-mode engaged: N candidate pairs; per-pair timeout=Xms; fall-through-after=Y`) हर बार चलने पर प्रदर्शित होती है — हमेशा दृश्यमान, गैर-TTY वातावरण में भी काम करती है। मजबूर रूप से stderr फॉल-थ्रू ट्रिगर इवेंट TTY-गेटिंग/`--progress` को बायपास करता है क्योंकि ऑपरेटर को मोड-स्विच देखना होगा। `contradictions.md` में नया `## Auto-mode fall-through` मार्कडाउन ब्लॉक, जब सीमा पार हो जाती है। हेयुरिस्टिक केवल अप्रसंस्कृत जोड़ों पर फिर से चलता है (पहले से ही LLM द्वारा पूर्ण किए गए जोड़ों का कोई दोहरा वर्गीकरण नहीं)।

### आर्किटेक्चरल नोट

R-019, रिसर्च-ओएस ↔ ollama-intern-mcp की सीमा को पार करता है। रिसर्च-ओएस `ollama_extract` स्कीमा में `tier_budget_ms_override` को पास करता है; ollama-intern-mcp v2.6.0 आंतरिक गार्डरेल पर इसका सम्मान करता है। यह बुनियादी ढांचा पहले से मौजूद था; v2.6.0 ने क्लाइंट-साइड एंट्री पॉइंट प्रदान किया; v0.13.0, रिसर्च-ओएस-साइड क्लाइंट कनेक्शन स्थापित करता है। R-018 का `Promise.race` रैपर बरकरार रखा गया है क्योंकि यह एक अलग प्रकार की विफलता से बचाता है (अनसॉल्व्ड-प्रॉमिस हैंग्स — रैपर इन हैंग्स को पकड़ सकते हैं; आंतरिक बजट पर संरचित `isError:true` पेलोड जिन्हें रैपर तक नहीं पहुंच सकता है, वह R-019 का क्षेत्र है)।

### नियमों की सीमा

सिस्टम नियमों का पालन किया गया। `accepted_claim_floor` अपरिवर्तित है। `FailureShape` enum में नौ मान हैं, जो अपरिवर्तित हैं। `RECOVERY_ACTIONS` enum में 8 मान हैं - कोई नया सलाहकार कार्रवाई नहीं; R-014 का विशिष्ट-आकार का अनुमान मौजूदा कार्यों के मार्ग को बढ़ाता है। AI पुनर्प्राप्ति सलाहकार प्रॉम्प्ट टेम्पलेट अपरिवर्तित है (नए `EvidenceState` फ़ील्ड स्थायी JSON में दिखाई देते हैं, लेकिन प्रॉम्प्ट में प्रदर्शित नहीं होते हैं)। पुनर्प्राप्ति सत्यापन नियमों में कोई बदलाव नहीं किया गया है। MCP आर्किटेक्चर अपरिवर्तित है - `ollama-intern-mcp@^2.4.0` का उपयोग जारी है; निष्कर्षण पर MCP कॉल आकार में कोई बदलाव नहीं है। R-017 की चेतावनी केवल सूचनात्मक है और गेट निर्णय, फ्रीज स्वीकृति या पैक प्रकाशन को प्रभावित नहीं करती है। सभी v0.10 + v0.11 सुरक्षा उपायों को बनाए रखा गया है; सुरक्षा आधार अपरिवर्तित है, और v0.12 इस पर आधारित है।

### research-os क्या नहीं है (और v0.12.1 क्या दावा नहीं करता)

- यह सुविधा अभी तक पूरी तरह से परीक्षण नहीं की गई है। v0.12.0 ने v0.3 के कुछ मुद्दों को ठीक कर दिया (सुरक्षा स्तर पर 'अकेलापन' सिद्ध; कवरेज स्तर पर 'अकेलापन' अभी तक सिद्ध नहीं है – v0.3 में प्राप्त 'सिद्धांत' लागू किया गया); v0.4 के परीक्षण में v0.12.0 ने 'शर्तों के साथ पास' (authorization-grade नहीं) का परिणाम दिया – सुरक्षा स्तर बरकरार है, कवरेज स्तर पर महत्वपूर्ण रूप से सुधार हुआ, लेकिन अंतिम चरण में एक विफलता का तरीका मौजूद है। v0.12.1 में उस विफलता के तरीके को ठीक किया गया है (R-018)। v0.4 का पुन: परीक्षण इस npm रिलीज़ के साथ एक अलग सत्र में किया जाएगा और यह अंतिम चरण के लिए आवश्यक है।
- बाहरी उपयोगकर्ताओं द्वारा इसका परीक्षण अभी तक नहीं किया गया है, सिवाय 'डॉगफूड' परीक्षणों और चार 'ऑपरेटर-अकेलापन' परीक्षणों के। छह 'डॉगफूड' प्रयोग पूरे हो चुके हैं – जिनमें से एक आत्म-संदर्भित है, और पांच बाहरी डोमेन (ComfyUI, XRPL, Godot, समीक्षक-कैलिब्रेशन, नियतात्मक-समीक्षक) से संबंधित हैं – साथ ही v0.1 / v0.2 / v0.3 / v0.4 के 'ऑपरेटर-अकेलापन' परीक्षणों में 18 ज्ञात मुद्दे सामने आए हैं (R-001 से R-005, v0.10.0 में बंद किए गए; R-007 से R-011, v0.11.0 में बंद किए गए; R-012 से R-017, v0.12.0 में बंद किए गए; R-018, v0.12.1 में बंद किया गया)। बड़े पैमाने पर बाहरी ऑपरेटरों का उपयोग भविष्य में किया जाएगा।
- यह एक पूर्ण पैकेज संश्लेषण लेखक नहीं है। v0.12.1, v0.9 के 'सेक्शन-स्कोप' (`synth section`) और 'आंशिक-पैकेज-स्कोप' (`synth pack --partial`) सुविधाओं को बरकरार रखता है, जिनमें से प्रत्येक में स्पष्ट रूप से पैकेज की उपयोगिता के बारे में जानकारी दी गई है। पूर्ण पैकेज संश्लेषण के लिए अभी भी एक `synthesis_ready` पैकेज और `synth workspace` के माध्यम से स्वीकृत दावा आईडी के खिलाफ मानव (या Cowork) द्वारा बनाया जाना आवश्यक है।
- यह किसी भी समीक्षक मॉडल का समर्थन नहीं करता है। v0.12.1 डिफ़ॉल्ट रूप से कोई `trusted_baseline` समीक्षक प्रोफ़ाइल प्रदान नहीं करता है; कैलिब्रेशन रसीदें समर्थन नहीं हैं, बल्कि प्रमाण हैं। मौजूदा v0.6.0 कैलिब्रेशन रसीदें v0.8.0 MCP आर्किटेक्चर से पहले की हैं और MCP पथ के तहत पुन: निर्धारित नहीं की गई हैं। [समीक्षक कैलिब्रेशन हैंडबुक पृष्ठ](https://mcp-tool-shop-org.github.io/research-os/handbook/reviewer-calibration/) देखें।
- इसमें पुराने तत्वों से मुक्त नहीं है। v0.4 से पहले के स्थिर पैकेजों में `research_os_version: '0.1.0'` होता है, क्योंकि v0.4 से पहले एक हार्डकोडेड 'स्काफॉल्ड' स्थिरांक का उपयोग किया गया था; यह सुधार v0.4.0 में किया गया था, लेकिन पुराने स्थिर पैकेजों को कानून 15 के तहत बदला नहीं जा सकता (देखें [`handbook/known-limitations`](https://mcp-tool-shop-org.github.io/research-os/handbook/known-limitations/)।
- यह npm पर 'प्रमाणित' नहीं है। Sigstore प्रमाणन भविष्य में उपलब्ध कराया जाएगा; v0.12.1 npm पैकेजों को पैकेज-shasum और GitHub रिलीज़ कमिट के माध्यम से सत्यापित करें।
- यह 'क्लाउड-आधारित' समाधान से बेहतर नहीं है। v0.7.x से `local-first-vs-cloud-research/` पर किए गए उत्पाद परीक्षणों में क्लाउड के फायदे (पढ़ने में आसानी और ऑपरेटरों पर बोझ) दिखाए गए थे; v0.12.1 यह दावा नहीं करता है कि इन फायदों को समाप्त कर दिया गया है।

### ज्ञात सीमाएँ

v0.12.1 में तीन ज्ञात सीमाएं हैं जो पिछले रिलीज़ से ली गई हैं और जो उपयोगकर्ताओं को दिखाई देती हैं। प्रत्येक को [हैंडबुक ज्ञात-सीमाएं पृष्ठ](https://mcp-tool-shop-org.github.io/research-os/handbook/known-limitations/) और [CHANGELOG.md](CHANGELOG.md) में प्रलेखित किया गया है। इनमें से कोई भी रिलीज़ को अवरुद्ध नहीं करता है; सभी के लिए एक परिभाषित रिकवरी या निवारण का तरीका मौजूद है।

- **B-E-001 — pre-v0.4 फ्रोजन-पैक संस्करण स्टैम्प एक ऐतिहासिक अवशेष है।** v0.3.3 से v0.6.0 तक प्रकाशित फ्रोजन पैकों में `pack.manifest.json` और `pack/research.yaml` फ़ाइलों में `research_os_version: "0.1.0"` लिखा हुआ है, क्योंकि यह v0.4 से पहले एक हार्डकोडेड स्केफॉल्ड कांस्टेंट था। यह सुधार v0.4.0 में लागू किया गया था (अब स्केफॉल्ड लाइव `RESEARCH_OS_VERSION` को इम्पोर्ट करता है); पहले के फ्रोजन पैकों को लॉ 15 के तहत अपरिवर्तनीय माना जाता है। प्रभावित पैकों के अंदर मौजूद ऑडिट JSON फ़ाइलों में उनके वर्तमान संस्करण मौजूद हैं।
- **B-E-004 — npm प्रोवेनेंस एटेस्टेशन को भविष्य में जारी होने वाले संस्करण में स्थानांतरित किया जाएगा।** v0.12.1 npm टारबॉल केवल पैकेज-शासम के माध्यम से सत्यापित होता है। प्रकाशन प्रक्रिया को एक CI वर्कफ़्लो में स्थानांतरित करने से सिग्स्टोर OIDC के साथ टकराव होता है, जो प्रकाशन से पहले अनुवाद की आवश्यकता (TranslateGemma 12B स्थानीय रूप से चलता है); यह परिवर्तन भविष्य में जारी होने वाले संस्करण में किया जाएगा। v0.12.1 npm पैकेजों को पैकेज-शासम और GitHub रिलीज़ कमिट के माध्यम से सत्यापित करें।
- **B-A-003 — इंडेक्सर स्कीमा-संस्करण माइग्रेशन प्रलेखित है, लेकिन लागू नहीं है।** v0.12.1 में एक राइट-साइड `SCHEMA_VERSION` पूर्णांक शामिल है, लेकिन कोई रीड-साइड माइग्रेशन रनर नहीं है। प्रलेखित `SCHEMA_VERSION` अपडेट होने पर, `.research-os/index.sqlite` फ़ाइल को हटा दें और `research-os index build --all` कमांड को फिर से चलाएं। स्वयं पैक पर इसका कोई प्रभाव नहीं पड़ता है - इंडेक्सर साक्ष्य + दावों पर एक त्वरण परत है (लॉ 8); पुनर्निर्माण idempotent है।

v0.12.1 में कोई भी `trusted_baseline` समीक्षक प्रोफ़ाइल स्वीकार नहीं किया जाता है। यह एक जानबूझकर किया गया विश्वास-आधारित निर्णय है, कोई कमी नहीं: रिपॉजिटरी में मौजूद कैलिब्रेशन रसीदें (`hermes-two-pass=failed`, `mistral-nemo-two-pass=conditional_pass`, `hermes-single-pass=comparison_only`, `hermes-two-pass-deterministic=failed`) इस साक्ष्य को दर्ज करती हैं। विश्वास बार-बार किए गए सीडेड-विफलता रिकॉल के माध्यम से अर्जित किया जाता है, न कि अनुमानित। ये रसीदें v0.8.0 MCP आर्किटेक्चर से पहले की हैं और MCP पथ के तहत फिर से बेसलाइन नहीं की गई हैं।
